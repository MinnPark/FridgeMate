> RAG 검색 코드를 점검하다 찾은 품질 문제와 그 수정 내역입니다. 사전지식 없이 읽도록 평문으로 적었습니다.

## 변경 1. RAG-Fusion 후보풀이 너무 작아 "융합"이 형식만 남던 문제
- **증상**: Fusion이 쿼리 4개를 만들어 검색은 하는데, 합친 결과가 단일 검색과 별 차이가 없었다.
- **원인**: 서브쿼리마다 최종 반환 개수(k, 예: 3개)만큼만 뽑은 뒤 RRF로 합쳤다. 후보가 4쿼리×3=최대 12개뿐이라, RRF(여러 결과 리스트에서 공통으로 위에 오른 항목을 끌어올리는 기법)가 효과를 낼 풀이 부족했다 → 사실상 융합이 형식만 남음.
- **해결**: 서브쿼리 검색은 넓게(`k*3`, 최소 20개) 뽑고, RRF로 합친 뒤 최종 k개로 자르도록 변경. (`backend/app/rag/rag_fusion.py`)
- **결과**: 여러 쿼리에서 공통으로 잡힌 레시피가 제대로 상위로 떠서 융합 효과 확보.

## 변경 2. HyDE와 Fusion의 점수 스케일이 달라, 섞으면 Fusion이 바닥에 깔리던 문제
- **증상**: 식단처럼 여러 끼니 검색 결과를 한 리스트에 모아 정렬하면, Fusion으로 찾은 레시피가 항상 뒤로 밀렸다.
- **원인**: HyDE·일반검색은 "1 − 거리"(대략 0.7 스케일) 점수를, Fusion은 "RRF 점수"(대략 0.02 스케일)를 썼다. 점수 체계가 달라 같은 리스트에서 비교하면 Fusion이 무조건 낮게 깔림. 게다가 cosine 거리는 1을 넘을 수 있어 "1−거리"가 음수가 되기도 했다.
- **해결**: (a) "1−거리"가 0 미만이면 0으로 막고(클램프), (b) 각 결과 리스트 안에서 점수를 0~1로 정규화(min-max)해 **전략과 무관하게 같은 스케일**로 맞춤. (`backend/app/rag/integration.py` 의 `_normalize_scores`)
- **결과**: HyDE·Fusion·일반검색 결과를 섞어도 공정하게 정렬(각 리스트 1위 = 1.0).

## 변경 3. 전략 선택 길이 기준 불일치 통일
- **증상**: "쿼리 길이 10자 미만이면 HyDE" 규칙인데, 코드마다 **"공백 제거 길이"** 와 **"공백 포함 길이"** 가 섞여 경계(9~11자) 케이스에서 다르게 판정될 수 있었다.
- **해결**: RAG 쪽(`integration.search`, `smart_search`)을 에이전트(`recipe_agent.choose_rag_strategy`)와 동일한 **"공백 제거 길이"** 기준으로 통일.
