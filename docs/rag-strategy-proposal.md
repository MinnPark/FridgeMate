# RAG 전략 라우팅 제안 (에이전트쪽 검토용) — PLAIN/HyDE/Fusion/MERGE 실험 (2026-06-07)

> 작성: B파트(RAG). 대상 독자: 에이전트/그래프 담당(A파트, `recipe_agent.choose_rag_strategy`).
> 목적: 현재 "길이로 HyDE/Fusion 택1" 라우팅이 최적인지 실측으로 검토 + 대안 제안.

## 1. 현재 동작
- `recipe_agent.choose_rag_strategy`: 공백제거 길이 <10 → **HyDE** / else → **RAG-Fusion**. (Basic/plain은 LLM 실패 시 폴백으로만)
- 즉 라이브는 매 쿼리 HyDE 또는 Fusion **하나만** 탐. plain(순수 벡터)은 의도적으론 안 씀.

## 2. 실험 설계
- 8케이스(장르 한·양·중·일 × 길이 짧음/묘사). 각 쿼리를 **plain / hyde / fusion 모두** 실행(k=10) + 셋을 **RRF로 병합(merged)** + 케이스별 최고(oracle).
- relevance = recipe_db 1,693 이름 부분일치(투명·재현). 지표 P@3/P@5/R@5/MRR.

## 3. 결과 (엔진별 평균, 8케이스)
| engine | P@3 | P@5 | R@5 | MRR |
|---|---|---|---|---|
| plain (순수 벡터) | 0.71 | 0.65 | 0.38 | 0.938 |
| hyde (로컬 7b) | 0.54 | 0.50 | 0.29 | **0.698** (최약) |
| fusion (로컬 7b) | 0.67 | 0.60 | 0.28 | 0.893 |
| **merged (3-way RRF)** | **0.79** | **0.67** | **0.42** | **1.000** |
| oracle (케이스별 best) | 0.75 | 0.68 | 0.42 | 1.000 |

케이스별 최고 엔진: **plain 7/8**, fusion 1/8(중식 묘사형). **HyDE가 단독 최고인 케이스 0건.**

## 4. 발견
1. **3개 병합(merged)이 최고** — P@3 0.79 / MRR 1.000. 단일 어떤 엔진보다, 심지어 oracle(케이스별 best 선택)보다도 P@3 높음. 여러 엔진이 공통 상위로 올린 레시피가 RRF로 떠올라서.
2. **plain(순수 벡터)이 단일 최강**(MRR 0.938), **HyDE(로컬 7b)가 최약**(0.698). 원인: 로컬 qwen 가상문서 노이즈 — 일부 케이스에서 **가상문서를 중국어로 출력**(예: "名称：番茄酱意面…", "三文鱼盖饭…"), `{name}` 미치환, "스테이크"로 유도 등.
3. **현재 라우팅은 짧은 쿼리에 HyDE(최약)를 강제** → plain보다 손해. (짧은 요리명일수록 plain이 더 정확)

## 4-2. 서브모델 비교 (묘사형 강화·누수 확인)
같은 5케이스(중식짧 1 + 묘사형 4)를 **서브쿼리 LLM만 교체**해 실행(라우팅 동일).

| 서브모델 | 위치 | P@3 | P@5 | R@5 | MRR | 멀티쿼리 다양성 | 누수/노이즈 |
|---|---|---|---|---|---|---|---|
| qwen2.5-7b (현재) | LM Studio 로컬 | 0.67 | 0.52 | 0.39 | 0.867 | 보통(일부 오프타깃) | 외국어 토큰("토란 potrà"), 중국어 가상문서, 오타 |
| gpt-oss-20b | LM Studio 로컬 | 0.67 | 0.56 | 0.46 | 0.867 | **나쁨** (원쿼리+"레시피/추천/요리"만 접미 → 다각화 0) | 다양성 누수 |
| claude-haiku | OpenRouter | 0.47 | 0.44 | 0.52 | 0.750 | **최고** (사천식·마라두부 등 도메인 다각화) | 드물게 토큰깨짐("파게티","마 스타"), 과다양화 |

**하드 케이스 (중식·묘 "두부 들어간 매운 중국요리")**:
- qwen / gpt-oss: P@3 0.33, MRR 0.333 (마파두부 못 띄움)
- **claude-haiku: P@3 0.67, R@5 1.00, MRR 1.000** — '사천식 매운 두부'·'마라두부'로 다각화해 적중

**발견**
1. **큰 모델 ≠ 자동 향상**: gpt-oss-20b는 멀티쿼리를 단순 접미로만 늘려 다각화 실패(qwen과 평균 동률).
2. **강한 모델(claude)의 가치는 "진짜 어려운 묘사형"에서 나옴** — 하드 중식 케이스를 P@3 2배·MRR 0.33→1.0으로 살림. 단 쉬운 케이스(양식/일식)에선 과다양화·토큰깨짐으로 평균 P@3는 오히려 하락.
3. claude 평균 P@3가 낮은 건 **부분적으로 metric artifact** — 이름일치 relevance가 claude의 의미적 다양화(이름 다른 정답)를 과소평가. 의미기반 relevance면 결과 달라질 수 있음.
4. **누수 정리**: qwen=외국어/중국어 토큰 혼입 · gpt-oss=다양성 없음 · claude=드문 토큰깨짐.

## 5. 제안 (택1, 에이전트쪽 결정)
| 안 | 내용 | 근거 | 비용 |
|---|---|---|---|
| **A. RAG가 3개 병합 반환 (추천)** | retrieve_recipes가 plain+hyde+fusion 돌려 **RRF 병합** 결과 반환. ("3개 다 처리해 베스트" = 병합으로 구현, oracle 선택 불필요) | merged 최고(P@3 0.79/MRR 1.0) | 쿼리당 ~2 LLM콜+6검색 (식단 다건이면 가중) |
| **B. 저비용 라우팅 수정** | 짧음→**plain**(HyDE 말고), 김→Fusion. | 로컬 HyDE가 plain보다 나쁨 | 단일 검색 유지(LLM 0~1콜) |
| **C. 서브LLM을 Claude로** | RAG_LLM_PROVIDER=openrouter | hyde/fusion 품질↑(가상문서·멀티쿼리 정제) → merged/A안 효과 더 커질 것 | 외부 LLM 비용 |

- **즉시 효과·저비용** = B (짧은쿼리 plain). **최고 품질** = A (3병합), 단 비용 큼 → 캐시·결과수 조절 병행 권장.
- A는 "RAG가 다 처리해서 준다"는 설계로, **에이전트는 strategy 신경 안 쓰고 retrieve_recipes만 호출**하면 되는 단순화 이점도 있음.

**서브모델 선택 (4-2 근거)**: 묘사형 강화엔 **Claude(강한 모델)가 유효**하나 쉬운 케이스 부작용+비용 → **긴 묘사쿼리만 Claude, 짧은건 plain/local** 하이브리드가 합리. **gpt-oss-20b는 멀티쿼리 다각화를 못 내 비추**(현 프롬프트 기준). 즉 "모델 키우기"보다 **(B) 짧음=plain + (긴쿼리 Fusion만 Claude)** 조합이 비용대비 최선으로 보임.
