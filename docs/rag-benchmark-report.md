# RAG 검색 성능 실험 보고서 — 126쿼리 (PLAIN vs SMART)

> 측정 2026-06-09 · 하네스 `scripts/rag_eval_bulk.py` · 코퍼스 `recipe_db` 1,693건(embed_sig `bge-m3-1024`)
> 방법론·지표 정의: `docs/rag-eval-methodology.md` / 쉬운 설명: `docs/rag-easy-guide.md`

## 0. 한 줄 결론 (중요)

**표본을 16 -> 126쿼리로 키우자, SMART(HyDE/RAG-Fusion+RRF)가 PLAIN보다 전반적으로 낮게 나왔다.**
(P@3 76% -> 59%, MRR 0.72 -> 0.52). 이전 16쿼리 소표본의 "SMART가 P@3 +25%p" 라는 결론은 **표본이 작고 유리한 run** 이었고, 큰 표본에선 뒤집힌다. 원인은 §4.

---

## 1. 실험 설계 (표본/모수)

- **표본 n = 126쿼리**, 두 층(stratum):
  - **재료조합 110** — 코퍼스에서 레시피 110개(이름 중복 제거, 재료 4개 이상) 무작위 샘플(seed=42). 각 레시피의 **재료 상위 4개**를 쿼리로, 정답 = 그 레시피 이름. (예: `연두부 칵테일새우 달걀 생크림` -> 새우두부계란찜)
  - **수작업 16** — 기존 `rag_eval.py`의 오타4·묘사8·구어4.
- **정답 매칭**: 이름 기준(동명 레시피는 같은 요리로 hit 인정).
- **검색 깊이** k=5. 지표: P@1, P@3, Hit@5(=Recall@5, 단일정답), MRR.
- **PLAIN** = 순수 bge-m3 벡터(결정적). **SMART** = `smart_search`(길이로 HyDE/Fusion 분기, 서브쿼리 LLM = 로컬 qwen2.5-7b).
- **주의**: SMART는 LLM 비결정 -> **1회 측정치**(이상적으론 3~5회 평균; §5 한계). 코퍼스는 읽기만.

> 재료조합 쿼리의 성격: 재료 4개는 **이미 키워드가 풍부**해서 순수 벡터검색에 유리하다. 이 점이 결과 해석의 핵심(§4).

---

## 2. 결과 — 전체

| 지표 | PLAIN | SMART | 차이 |
|---|---|---|---|
| P@1 | **65.1%** | 43.7% | **-21.4%p** |
| P@3 | **76.2%** | 58.7% | **-17.5%p** |
| Hit@5 | **82.5%** | 62.7% | -19.8%p |
| MRR | **0.720** | 0.517 | -0.203 |

95% Wilson CI: PLAIN P@3 **68–83%**, SMART P@3 **50–67%** -> **구간이 거의 안 겹친다**(n=126이라 신뢰구간이 16쿼리 때보다 훨씬 좁다). 차이는 노이즈가 아니라 **실제 하락**으로 본다.

## 3. 결과 — 층화 (어디서 갈리나)

| 층 | n | PLAIN P@3 | SMART P@3 | 차이 | 해석 |
|---|---|---|---|---|---|
| 재료조합 | 110 | **77%** | 56% | **-21%p** | SMART가 키워드 쿼리를 망침(아래 §4) |
| 오타 | 4 | 100% | 100% | 0 | 둘 다 완벽(bge-m3 오타 강함) |
| 묘사 | 9 | 56% | 56% | 0 | 동률 |
| 구어 | 3 | 67% | 100% | +33%p | SMART 유리하나 **n=3, 통계적 의미 없음** |

핵심: **하락의 거의 전부가 "재료조합 110"에서 나온다.** SMART가 이득을 보이는 건 구어(n=3)뿐이고 표본이 너무 작다.

---

## 4. 원인 분석 (왜 SMART가 더 나빴나)

1. **키워드 쿼리를 LLM이 재작성하면 오히려 망가진다.** 재료조합 쿼리(`팥 설탕 현미 ...`)는 이미 검색에 최적이라, RAG-Fusion이 이를 "다각도 쿼리"로 바꾸면 **엉뚱한 요리로 드리프트**(예: 재료만 비슷한 다른 레시피)해서 정답이 밀린다. PLAIN은 원 키워드를 그대로 써서 정확.
2. **로컬 qwen2.5-7b의 출력 품질·오류.** 실행 로그에 LLM 400 에러(`Failed to parse input ... 설�ugar` 같은 **깨진/혼합문자** 생성)와 잡문(`사무엘로 볶아`)이 다수. LLM 실패 시 plain 폴백되지만, **성공하더라도 저품질 서브쿼리**가 검색을 흐린다.
3. **HyDE/Fusion이 빛나는 구간은 좁다.** 짧은 오타는 bge-m3가 이미 100%, 서술/구어는 표본이 작다. 즉 고급기법이 이득을 볼 영역(모호·표현간극 큰 쿼리)이 이 126셋에선 비중이 작고, 다수(재료조합)에선 손해다.

> 요약: **현재 서브쿼리 LLM(로컬 qwen-7b) + 키워드성 쿼리** 조합에서 SMART는 순이익이 아니라 순손실.

---

## 5. 한계 (정직하게)

- **SMART 1회 측정**(LLM 비결정). 이상적으론 3~5회 mean±std. 단, 하락폭(-17%p P@3)이 크고 CI가 안 겹쳐 방향은 견고.
- **재료조합 쿼리는 보수적 라벨**: 재료가 겹치는 다른 레시피가 위로 와도 miss 처리 -> 절대 수치는 낮게 나오는 경향. 단 **PLAIN/SMART가 같은 쿼리/라벨**을 받으므로 **비교(델타)는 유효**.
- 코퍼스 1,693 1회 스냅샷. 재인덱싱/코퍼스 변경 시 재측정 필요.
- 구어 n=3 등 일부 층은 표본이 작아 단독 결론 불가.

---

## 6. 권고 (실행 가능한 것)

1. **기본을 PLAIN로 두는 것을 검토.** 적어도 키워드·재료성 쿼리는 PLAIN이 명확히 낫다.
2. **SMART는 좁게 라우팅.** "짧고 모호/서술형"에만 HyDE/Fusion을 쓰고, 키워드가 충분한 쿼리는 PLAIN 직행하는 게이트를 추가.
3. **서브쿼리 LLM 업그레이드 재실험.** 로컬 qwen-7b 대신 더 강한 모델(예: Claude)로 HyDE/Fusion을 돌려 같은 126셋 재측정 — 티어링 비용 대비 이득 검증.
4. **로컬 LLM 출력 안정화.** qwen의 깨진 출력(400) 빈도를 줄이거나(프롬프트/파라미터), 실패 즉시 plain 폴백 명확화.
5. **표본 확대 + SMART 다회**로 §4 가설(키워드에서 손해/모호에서 이득) 을 층별로 정밀 검증.

## 7. 재현

```bash
cd backend
.venv\Scripts\python.exe scripts\rag_eval_bulk.py --mode both --n 110 --seed 42
# 옵션: --mode plain|smart  --smart-cap N(SMART 쿼리 상한)
```

- SMART 수치는 run마다 변동(LLM) — 여러 번 돌려 평균 권장.
